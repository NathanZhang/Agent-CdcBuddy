## 一、部署手册总览与适用场景

### 1.1 平台定位与部署目标
**Agent-CdcBuddy** 专为疾控中心及爱卫办业务打造，平台集成了大语言模型（LLM）、LangGraph 状态图机、PyTorch 双向 LSTM、SaTScan 时空扫描算法、分布式滞后非线性模型（DLNM）及微前端 AG-UI 生成式组件。

为确保系统在不同交付环境下稳定可靠运行，本手册详细规范了从**零基础裸机配置**、**依赖安装**、**五大数据库底座初始化**，到**多智能体集群启停**、**Docker 容器化交付**及**国产信创数据库迁移**的标准操作规程。

### 1.2 四大部署形态对照

| 部署形态 | 适用阶段 | 进程/容器结构 | 数据持久化方式 | 维护复杂度 |
| :--- | :--- | :--- | :--- | :---: |
| **形态 1：单机轻量开发/演示** | 本地开发、专家功能评审、临时演示 | 单进程 Next.js dev 模式 (`3000` 或 `3001`) | 本地 SQLite (`.db` 文件) | 极低 |
| **形态 2：物理机/虚机集群** | 疾控内网私有虚机、长期测试环境 | 4 个独立 Next.js 进程 (端口 `3001~3004`)，由 `./server.sh` 统一管理 | 本地 SQLite (`.db` 文件) | 中等 |
| **形态 3：Docker Compose 容器集群** | 标准化交付、DevOps 流水线、云原生环境 | 4 个容器共享网络，挂载宿主机事实底座与持久化数据目录 | 宿主机目录挂载卷 (`./data`) | 低 |
| **形态 4：生产级信创高可用** | 省/市级疾控政务专网正式上线运营 | Nginx + Node.js 集群 + 本地/私有化 LLM 网关 | 人大金仓 KingbaseES / PostgreSQL 14+ | 企业级 |

## 二、基础环境要求与版本规范

### 2.1 硬件资源推荐矩阵

| 部署规模 | CPU 核心数 | 内存 (RAM) | 存储空间 (磁盘) | 适用场景 |
| :--- | :---: | :---: | :---: | :--- |
| **最低配置** | 4 核 | 8 GB | 20 GB SSD | 单智能体演示、本地研发联调 |
| **标准推荐配置** | 8 核 | 16 GB | 50 GB SSD | 全域四智能体集群运行、完整 44 项测试自动化回归 |
| **生产级高并发配置** | 16 核+ | 32 GB+ | 100 GB+ NVMe SSD | 省级疾控中心生产上线、对接私有化大模型推理推理机 |

### 2.2 操作系统兼容性列表
- **Linux 生产首选**：Ubuntu 22.04 / 24.04 LTS、Debian 11 / 12、CentOS 7.9 / Rocky Linux 8 / 9
- **国产信创系统**：统信 UOS 20 SP1+、银河麒麟 Kylin Linux Advanced Server V10
- **开发与调测系统**：macOS 13.0+ (Apple Silicon M 系列及 Intel 架构)、Windows 11 (WSL2 环境)

### 2.3 核心依赖组件版本矩阵

| 软件/组件名称 | 必须版本 | 推荐版本 | 作用与职责 |
| :--- | :---: | :---: | :--- |
| **Node.js** | `>= 18.18.0` | `v20.x LTS` 或 `v22.x LTS` | 前端渲染、Next.js 15 服务端路由、CopilotKit 运行时 |
| **Python** | `>= 3.9.0` | `3.10.x` 或 `3.11.x` | `analytics_engine` 算法引擎、PyTorch、LangGraph |
| **Docker Engine** | `>= 24.0.0` | `26.x+` | 容器化镜像构建与运行（适用于容器化部署） |
| **Docker Compose** | `>= 2.20.0` | `v2.24+` | 多容器集群统一编排（适用于容器化部署） |
| **Git** | `>= 2.30.0` | 任意稳定版 | 源码拉取与构建版本 Git Hash 提取 |

### 2.4 网络环境与端口规划矩阵

在疾控专网或云服务器部署时，需在防火墙或安全组开放以下监听端口：

| 端口号 | 协议 | 所属服务 / 智能体 | 访问范围 | 详细说明 |
| :---: | :---: | :--- | :--- | :--- |
| **3001** | TCP | `cdcbuddy-vector` | 内部/业务端 | 病媒生物与宿主动物监测预警智能体 |
| **3002** | TCP | `cdcbuddy-foodborne` | 内部/业务端 | 食源性疾病监测预警智能体 |
| **3003** | TCP | `cdcbuddy-env` | 内部/业务端 | 环境健康风险监测预警智能体 |
| **3004** | TCP | `cdcbuddy-chronic` | 内部/业务端 | 死因、慢病及伤害综合监测预警智能体 |
| **3000** | TCP | 默认单实例 / 容器内端口 | 内部/容器间 | 单智能体默认端口或 Docker 内部映射端口 |
| **80 / 443** | TCP | Nginx 反向代理网关 | 疾控内网用户 | 统一对外开放的 HTTP/HTTPS 服务网关入口 |

> [!NOTE]
> 系统后端会向配置的大模型 API 服务（如 `https://api.siliconflow.cn`）以及国家天地图 GIS 瓦片服务发起出站 HTTPS 请求，请确保服务器具备相应出网权限（或内网 HTTP 代理配置）。

## 三、源码获取与基础环境配置

### 3.1 源码克隆与权限准备
```bash
# 1. 克隆代码仓库
git clone https://github.com/NathanZhang/Agent-CdcBuddy.git
cd Agent-CdcBuddy

# 2. 赋予运维管理脚本执行权限
chmod +x server.sh start.sh stop.sh docker/entrypoint.sh
```

### 3.2 Node.js 运行时与前端依赖安装
```bash
# 检查 Node.js 版本
node -v # 输出需 >= v18.18.0，推荐 v20+

# 使用 npm 安装项目全部前端与服务端依赖
npm install
```

### 3.3 Python 独立虚拟环境与算法库安装
为保证科学计算引擎不受宿主机全局 Python 包污染，推荐使用独立虚拟环境（`server.sh` 在首次启动时亦会自动检查创建）：

```bash
# 1. 创建 Python 虚拟环境 .venv
python3 -m venv .venv

# 2. 激活虚拟环境
source .venv/bin/activate  # Linux/macOS
# Windows: .venv\Scripts\activate

# 3. 升级 pip 并安装全套科学计算、深度学习与 LangGraph 依赖
pip install --upgrade pip
pip install -r requirements.txt
```

> [!TIP]
> `requirements.txt` 包含了 PyTorch、Scikit-learn、SciPy、LangGraph、Pandas、NumPy 等算法模型库。在国内内网部署时，可配置清华镜像加速：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt`。

### 3.4 环境变量配置详解 (`.env.local`)
从模板复制环境变量配置文件：
```bash
cp .env.example .env.local
```

编辑 `.env.local` 文件，配置关键参数：
```env
# ==============================================================================
# 1. 大模型推理服务配置 (SiliconFlow / 私有化 vLLM / OpenAI 兼容接口)
# ==============================================================================
SILICONFLOW_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
SILICONFLOW_MODEL=Qwen/Qwen3.6-27B

# 大模型调度超时控制 (单位: 毫秒，默认 60000ms)
SILICONFLOW_ROUTER_TIMEOUT_MS=60000
SILICONFLOW_TEXT2SQL_TIMEOUT_MS=60000

# ==============================================================================
# 2. 国家地理信息公共服务平台 (天地图 Tianditu) 配置
# ==============================================================================
# 天地图浏览器端开发者 Key (申请地址: https://console.tianditu.gov.cn/)
NEXT_PUBLIC_TIANDITU_KEY=your_tianditu_browser_key_here

# ==============================================================================
# 3. 业务持久化数据库路径 (可选，默认使用工程根目录/容器目录下的 app_business.db)
# ==============================================================================
# APP_BUSINESS_DB_PATH=/path/to/custom/app_business.db
```

## 四、五大数据库底座全流程初始化

### 4.1 五数据库协同架构剖析
平台采用**四领域监测事实底座 + 一业务持久化闭环库**的五库协同架构：

```
                             [Agent-CdcBuddy 核心系统]
                                         │
       ┌──────────────────┬──────────────┴─────┬──────────────────┬─────────────────┐
       ▼                  ▼                    ▼                  ▼                 ▼
【病媒时空事实库】  【食源性监测事实库】  【环境健康事实库】  【死因慢病事实库】  【业务持久闭环库】
vector_monitoring    foodborne_monitoring    env_monitoring      chronic_monitoring  app_business.db
(5.6万+捕获/PCR)    (就诊/cgMLST/暴发)   (饮用水/污水/DLNM)   (证明书/ICD-10/4q70) (工单/预警/会话)
```

### 4.2 各数据库初始化操作指引

#### 1. 病媒生物监测事实库 (`vector_monitoring.db`)
- **数据特性**：只读事实表，内含河南省 18 地市 126 区县历年 5.6 万+ 条多维病媒生物捕获记录、PCR 病原筛查及抗药性测定事实数据（体积约 28MB）。
- **初始化方式**：
  - **同级目录自动复制**：若在同级目录存在 `Agent-CdcBuddy-DataMock`，执行 `./server.sh start` 时会自动检测并复制。
  - **独立服务器手动放置**：将提供的 `vector_monitoring.db` 文件直接放置于工程根目录下即可。

#### 2. 食源性疾病监测事实库 (`foodborne_monitoring.db`)
- **生成脚本**：`scripts/init_foodborne_mock.py`
- **内含核心表**：`fact_foodborne_case` (门诊病例)、`fact_pathogen_molecular` (致病菌 cgMLST 分子分型)、`fact_food_sampling` (食品抽样)、`fact_outbreak_event` (暴发事件)。
- **执行初始化**：
  ```bash
  python3 scripts/init_foodborne_mock.py
  ```

#### 3. 环境健康风险监测事实库 (`env_monitoring.db`)
- **生成脚本**：`scripts/init_env_mock.py`
- **内含核心表**：`fact_water_monitoring` (出厂水/末梢水/管网水质)、`fact_sewage_monitoring` (污水病原浓度与时序)、`fact_air_climate_monitoring` (空气质量与气温)、`fact_river_basin_monitoring` (流域跨介质污染链)、`fact_public_venue_inspection` (公共场所卫生评级)。
- **执行初始化**：
  ```bash
  python3 scripts/init_env_mock.py
  ```

#### 4. 死因、慢病及伤害综合监测事实库 (`chronic_monitoring.db`)
- **生成脚本**：`scripts/init_chronic_mock.py`
- **内含核心表**：`fact_death_registry` (8,500 条死因医学证明书及死因链)、`fact_chronic_cases` (12,000 条慢病随访队列)、`fact_injury_surveillance` (5,000 条伤害门诊就诊记录)、`dim_districts` (全省人口统计)。
- **执行初始化**：
  ```bash
  python3 scripts/init_chronic_mock.py
  ```

#### 5. 业务持久化闭环数据库 (`app_business.db`)
- **生成脚本**：`scripts/init_business_db.py`
- **内含核心表**：`biz_disposal_tickets` (消杀处置工单)、`biz_early_warning_events` (分级预警事件)、`biz_mobile_submissions` (移动端审核)、`biz_kb_standards` (国家标准知识库)、`biz_user_sessions` (会话与推理持久化)。
- **执行初始化**：
  ```bash
  python3 scripts/init_business_db.py
  ```

### 4.3 一键全库自动化初始化命令
系统提供一键执行指令，可一口气完成全部 4 个生成式数据库的初始化建表与种子数据填充：

```bash
# 一键完成四大领域数据库初始化
python3 scripts/init_business_db.py && \
python3 scripts/init_foodborne_mock.py && \
python3 scripts/init_env_mock.py && \
python3 scripts/init_chronic_mock.py
```

执行完成后，根目录下应包含全部 5 个 `.db` 数据库文件：
```bash
ls -lh *.db
# -rw-r--r--  1 root root  12M app_business.db
# -rw-r--r--  1 root root  18M chronic_monitoring.db
# -rw-r--r--  1 root root  15M env_monitoring.db
# -rw-r--r--  1 root root  14M foodborne_monitoring.db
# -rw-r--r--  1 root root  28M vector_monitoring.db
```

### 4.4 生产级 PostgreSQL / 人大金仓信创迁移

## 五、主机/虚拟机服务运维与集群管理 (`server.sh`)

平台配备了企业级运维脚本 `server.sh`，内置环境自检、Python 虚拟环境管理、隔离构建缓存 (`.next_<domain>`) 与进程守护。

### 5.1 运维脚本架构与命令总览
```bash
./server.sh {start|stop|restart|status|test|logs} [vector|foodborne|env|chronic|all] [dev|prod]
```

### 5.2 单智能体独立启动与调试
可按业务科室需求，单独启动某一领域的智能体：

```bash
# 启动病媒生物智能体 (监听端口 3001)
./server.sh start vector dev

# 启动食源性疾病智能体 (监听端口 3002)
./server.sh start foodborne dev

# 启动环境健康智能体 (监听端口 3003)
./server.sh start env dev

# 启动死因慢病伤害智能体 (监听端口 3004)
./server.sh start chronic dev
```

### 5.3 全域四智能体集群一键启停
在生产或联调阶段，可直接管理全域 4 个智能体实例：

```bash
# 【常用】一键启动全部 4 个智能体开发集群
./server.sh start all dev

# 一键启动生产编译集群 (会自动执行 Next.js build 优化打包)
./server.sh start all prod

# 停止全域集群
./server.sh stop all

# 重启全域集群
./server.sh restart all dev
```

### 5.4 状态监控、PID 管理与实时日志
```bash
# 查看所有智能体当前进程 PID 与端口健康状态
./server.sh status

# 实时查看指定智能体控制台日志 (Ctrl+C 退出)
./server.sh logs vector
./server.sh logs chronic
```

### 5.5 Linux systemd 系统守护进程配置
在 Linux 生产服务器中，推荐创建 systemd 服务以实现开机自启与崩溃自愈。以 `cdcbuddy.service` 为例：

创建 `/etc/systemd/system/cdcbuddy.service`：
```ini
[Unit]
Description=CdcBuddy Multi-Agent Cluster Service
After=network.target

[Service]
Type=forking
User=root
WorkingDirectory=/opt/Agent-CdcBuddy
ExecStart=/opt/Agent-CdcBuddy/server.sh start all prod
ExecStop=/opt/Agent-CdcBuddy/server.sh stop all
ExecReload=/opt/Agent-CdcBuddy/server.sh restart all prod
Restart=on-failure
RestartSec=10
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

启用并启动系统服务：
```bash
sudo systemctl daemon-reload
sudo systemctl enable cdcbuddy.service
sudo systemctl start cdcbuddy.service
sudo systemctl status cdcbuddy.service
```

### 5.6 生产级 Nginx 反向代理配置与网关分发
在对外提供统一入口时，可通过 Nginx 将四大领域智能体根据路径或子域名进行转发：

```nginx
# 统一反向代理网关配置示例
upstream vector_backend {
    server 127.0.0.1:3001;
    keepalive 32;
}
upstream foodborne_backend {
    server 127.0.0.1:3002;
    keepalive 32;
}
upstream env_backend {
    server 127.0.0.1:3003;
    keepalive 32;
}
upstream chronic_backend {
    server 127.0.0.1:3004;
    keepalive 32;
}

server {
    listen 80;
    server_name cdc-ai.local;

    # 客户端上传与超时配置
    client_max_body_size 50M;
    proxy_read_timeout 300s;
    proxy_connect_timeout 60s;

    # 1. 病媒生物智能体 (默认首页与 /vector/)
    location / {
        proxy_pass http://vector_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        
        # 支持 SSE 流式传输 (针对大模型思考链)
        proxy_set_header Connection '';
        proxy_http_version 1.1;
        chunked_transfer_encoding off;
        proxy_buffering off;
        proxy_cache off;
    }

    # 2. 食源性疾病智能体
    location /food/ {
        proxy_pass http://foodborne_backend/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 3. 环境健康智能体
    location /env/ {
        proxy_pass http://env_backend/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 4. 死因慢病伤害智能体
    location /chronic/ {
        proxy_pass http://chronic_backend/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

## 六、Docker 容器化与 Docker Compose 编排部署

### 6.1 Dockerfile 分层构建机制解析
平台提供的 `Dockerfile` 采用现代多阶段构建（Multi-Stage Build），确保生产容器镜像体积轻量（~600MB）、依赖隔离且运行安全：
1. **`dependencies` 阶段**：基于 `node:22-bookworm-slim` 纯净依赖安装。
2. **`builder` 阶段**：编译 Next.js 独立运行包（`standalone`），内嵌静态资源。
3. **`runtime` 阶段**：
   - 安装轻量 Python3 与 venv 独立虚拟环境，安装 `requirements.txt` 科学计算依赖。
   - 切换至非特权账号 `USER node` 执行，保障疾控内网主机安全。
   - 配置健康检查指令 (`HEALTHCHECK`) 自动探测服务存活。

## 八、常见故障排查与运维 FAQ

### Q1: 执行 `pip install -r requirements.txt` 时报错无法编译某些 C 扩展包？
- **原因**：宿主机缺少基础编译工具链（如 `gcc`, `g++`, `python3-dev`）。
- **解决方案**：
  ```bash
  # Ubuntu / Debian
  sudo apt-get update && sudo apt-get install -y build-essential python3-dev

  # CentOS / RHEL
  sudo yum groupinstall -y "Development Tools" && sudo yum install -y python3-devel
  ```

### Q2: 启动时提示 `【xxx】服务已在运行中` 或端口被占用？
- **原因**：之前的进程未正常退出或端口仍处于 `TIME_WAIT` / `LISTEN` 状态。
- **解决方案**：
  ```bash
  # 1. 尝试使用脚本停止
  ./server.sh stop all

  # 2. 若仍有残留，手动查杀对应端口
  lsof -i :3001 | awk 'NR>1 {print $2}' | xargs -r kill -9
  lsof -i :3002 | awk 'NR>1 {print $2}' | xargs -r kill -9
  lsof -i :3003 | awk 'NR>1 {print $2}' | xargs -r kill -9
  lsof -i :3004 | awk 'NR>1 {print $2}' | xargs -r kill -9

  # 3. 清理 pid 临时锁文件
  rm -f .server_*.pid .server.pid
  ```

### Q3: Docker 启动时提示 `/app/vector_monitoring.db is not mounted`？
- **原因**：未将宿主机上的 `vector_monitoring.db` 挂载至容器中。
- **解决方案**：
  - 检查宿主机根目录下是否存在 `vector_monitoring.db`（约 28MB）。
  - 在 `docker run` 时务必加上 `-v $(pwd)/vector_monitoring.db:/app/vector_monitoring.db:ro` 参数。

### Q4: 网页对话时长时间无响应，提示大模型调用超时？
- **原因**：
  1. `SILICONFLOW_API_KEY` 未配置或已失效；
  2. 网络无法访问大模型网关地址；
  3. 模型回复耗时超过设定阈值。
- **解决方案**：
  - 检查 `.env.local` 中的 `SILICONFLOW_API_KEY` 是否有效。
  - 在服务器上测试连通性：`curl -I https://api.siliconflow.cn/v1/models -H "Authorization: Bearer $SILICONFLOW_API_KEY"`。
  - 如模型推理较深，可在 `.env.local` 调大超时时间：`SILICONFLOW_ROUTER_TIMEOUT_MS=120000`。

### Q5: 天地图 GIS 地图组件显示为灰色或加载空白？
- **原因**：`NEXT_PUBLIC_TIANDITU_KEY` 未配置或 Key 类型不正确。
- **解决方案**：
  - 登录国家地理信息公共服务平台控制台，确认申请的是**“浏览器端 (Browser)”**类型的应用 Key，而非服务端 Key。
  - 配置于 `.env.local` 后需重启服务或重新构建容器。

### Q6: 高并发访问时 SQLite 报错 `database is locked`？
- **原因**：SQLite 为轻量级文件锁，在高并发写入场景下存在锁争用。
- **解决方案**：
  - 系统内置了 WAL (Write-Ahead Logging) 模式与重试机制以缓解锁冲突。
  - 若为市/省级高并发生产环境，强烈建议参考 [生产环境PostgreSQL及人大金仓迁移指南](docs/生产环境PostgreSQL及人大金仓(KingbaseES)迁移指南.md) 切换至人大金仓或 PostgreSQL 数据库。
